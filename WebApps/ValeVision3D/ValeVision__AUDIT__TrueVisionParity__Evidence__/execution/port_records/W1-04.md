## 1. Deviation from the package text: the SetOrbitMode seam is not applied (needs the orchestrator's eye)

The package lists two things that cannot both hold:

- vv_adaptations: "Na__NavToolbar__SetOrbitMode is the exit" (goal: "VV orbit setter"; R2 B.3.4 row: "W1-04 uses
  SetOrbitMode as the walk exit"), and
- acceptance item 3: "Transitions sections of Na__Test__SheetPagingWalkExit__ pass (suite ported whole in W1-36)",
  with W1-36's own adaptation "Na__Test__SheetPagingWalkExit__ reads 40__System__DrawingViewCore (no seam after W0-02)".

TV's test strips the module's imports and stubs exactly TV's names (SetActiveMode, ToggleWalkMode, ToggleFlyMode). A
ReturnToOrbit that calls Na__NavToolbar__SetOrbitMode throws `ReferenceError: Na__NavToolbar__SetOrbitMode is not
defined` there. This was measured, not assumed: the same scratch copy run against VV's pre-port 1.0.0 file (which
calls SetOrbitMode) crashes on its first Transitions check with exactly that error
(`scratch/W1-04/test__walkexit_transitions__before.log`, produced by `run_before_check.py` against
`backup__Na__DrawView__Transitions__.js.before`).

Resolution taken: TV's ReturnToOrbit body is kept verbatim, because in ValeVision it IS the Orbit button's exit:
VV's SetOrbitMode -> HandleOrbitClick -> index.html's wrappers `Na__UiFeature__WalkMode__ToggleFn('return-to-orbit')`
/ `Na__UiFeature__FlyMode__ToggleFn('return-to-orbit')` (index.html:2055-2091) -> `Na__UiFeature__ToggleWalkMode(null,
() => Na__NavToolbar__SetActiveMode('orbit'))` and the fly twin - the same two calls, in the same order, that TV's
body makes. Proven on ValeVision's own code by `scratch/W1-04/equivalence_check.mjs` (VV's REAL toolbar module wired
to index.html's REAL wrappers, cut out of index.html, against the REAL ported Transitions): for Walk, Fly and Orbit the
recorded calls, final modes, toolbar mode and dispatched `na-navigation-mode-changed` events are identical (5/5 PASS,
`test__equivalence_SetOrbitMode_vs_ReturnToOrbit.log`). It is also marginally more robust (it does not depend on the
toolbar having been initialised). Result: the file is TV's byte for byte apart from banner, console prefix and PORT
NOTE; all three acceptance items are satisfiable; W1-36 can port the suite with no seam, as it plans.

If the orchestrator or Adam prefers the planned seam: replace ReturnToOrbit's body with
`const left = Na__WalkMode__IsActive() || Na__FlyMode__IsActive(); if (left) Na__NavToolbar__SetOrbitMode(); return left;`
and its three imports with VV's SetOrbitMode import, and W1-36 must then add a SetOrbitMode stub to the test (a seam
it does not list). Not recommended.

The other two listed adaptations needed no code: "MaxEngine culling" - W0-02 already moved DistanceCulling to TV's path
(`05__RenderPipeline/Na__RenderEffect__DistanceCulling__.js`, DR-04 / K2 ruling 10), so TV's import line is used
verbatim; "Initialize kept" - the function is identical in both apps and index.html:2248 still calls it (not edited);
the PORT NOTE records that VV initialises it (controls disabled during a drawing, FlyTo flies), unlike TV.

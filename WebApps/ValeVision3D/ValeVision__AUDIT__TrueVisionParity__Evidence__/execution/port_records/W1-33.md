## 1. Decisions taken inside the package (for the orchestrator's eye)

### 1.1 The web viewer's first drawing is uncovered until W4-09 - a gap the plan's sequencing opens (ISSUE)

The plan says to call FirstOpen "when not in the web viewer and not Quiet, at TV's call site" (R4 D.1.4 item 3,
F.6.1, canonical "TV ModeController :733"), and this package does exactly that. But TV added the viewer half of that
guard in **v2.156.0**, with the published loading screen, because TV's viewer renders nothing since v2.155.0 and has
its own cover on every tab press. This app's viewer still renders sheets on the device until **W4-09** lands the
published viewer. Before this package the loader's full-screen screen (z 9999) waited for the drawing in the viewer
too; now the loader drops its cover after Enter, the host (appended after the cover, same z 600) paints above it, and
in viewer mode no first-open veil is built. So on the **live, read-only site** (viewer mode: not editable and
`LayoutEditor__WebViewer__Enabled: true`) a Vale client's first drawing of a session fills in uncovered once the
editor has loaded - only for projects whose Layout Mode is on. Localhost (editable) is unaffected, so the
orchestrator's localhost smoke test will not show it.

I did not change the plan's condition (it is explicit, and policy 11 forbids unlisted seams). The code comment over
the call says so in this app's words (recorded among the PORT NOTE's VV-worded comments). Two ways to close it, for
the orchestrator or Adam to choose before W1 is deployed:
- **(a) one-line VV seam until W4-09:** drop `!Na__LeVw__IsViewerMode() && ` from the call
  (`Na__LayoutEditor__ModeController__.js:678`) and list it under Divergences; W4-09 puts TV's guard back with the
  published loading screen. The in-host veil then covers the viewer's first drawing as it does the editor's.
- **(b) accept the gap** until W4-09 and simply do not deploy W1-W3 to the live site before W4-09.

### 1.2 DR-39 part 3 ("a veil for the first drawing after a document tab") is met by TV's own rule, with no loader screen

DR-39's option text for part 3 says "the loader shows its screen and waits on WaitForFirstDrawing" (the S03a design,
D-S03a-11). Since this package ports TV's FirstOpen, TV's once-per-session rule does that job: a Quiet entry under a
document tab does not spend `Na__LeVeil__FirstUsed`, so the first drawing tab afterwards gets the in-host veil (550ms
rule, the editor already loaded) - exactly TV's behaviour and acceptance item 2's "editor already loaded: the in-host
veil after 550 ms only if still drawing". A loader screen on top would be a second cover over the same wait (the
duplication VV v2.70.0 avoided) and not TV's look. So the loader never waits on the drawing (R4 D.1.4 item 6).

### 1.3 WaitForFirstDrawing keeps its export and its new rule, with no caller left

The canonical brief asks both for "hide the boot veil straight after action(editor)" and "WaitForFirstDrawing resolves
at once off the sheet view". Both are done: the loader no longer calls it, and the ModeController's export (a listed
VV seam) answers at once when not active or off the sheet view, otherwise waits on DrawingSettled. W4-09's "resolves
at once in the viewer" can still be added there if a caller returns. Its comment says it is kept for a caller that must
know when the open sheet is on the paper.

### 1.4 The one file outside my edits list: W1-31's Na__Test__LoaderFacade__.test.mjs (unavoidable importer update)

The test runs the real loader and loading screen and read four things this package's mandated changes retire: the
title's class (`.loading-text`), the status line's class (`.na-le-loading__status`), the loader's drawing-count line
in `Na__LeLoad__AwaitFirstDrawing` (static check D) and the drawing count driven through the loader (sections F and G).
Without an update the wave's G5 run fails on my files. Each check was rewritten to the same concern under the new
design and nothing else was touched:
- D: the drawing-count line is the first-open veil's - this app's LoadingVeil reads `VeilDrawingViews` with TV's
  fallback "Drawing the Views" - and the loader's code names neither `VeilDrawingViews` nor `WaitForFirstDrawing`.
- F: the headline read from `.na-le-veil__text`; the status line from `.na-le-veil__status`, which must read "Fetching
  the Drawing Tools" at the press and "Reading the Drawing Settings" last, with no WaitForFirstDrawing call.
- G: the case that drove a configured drawing label through the loader is retired with the loader's drawing line (its
  concern is covered by D); the section title loses "the label is the config's".
- header DESCRIPTION bullet and a 1.0.1 log entry with `{{VVREL:W1-33}}`.
Result: 117/117 (the two designed CheckNames failures of W1-31 F1 now pass with the rows added). The test is on no
hot-file register; only W1-31 lists it.

### 1.5 The new body-class checks live in the scratch harness, not in the suite

The early class and every path that drops it (acceptance item 3), the hand-over order (item 5) and the `immediate`
mechanics are proved by `execution/scratch/W1-33/verify_w1_33.mjs` (66 checks: the real LoadingVeil, LoadingScreen and
Loader in a fake DOM, per-case copies in the OS temp folder; TV read with git show at the pin). Adding them to W1-31's
test would go beyond an unavoidable importer update, so they stay in scratch, as W1-32 kept its harness. Follow-up 6
proposes folding them into the suite.

### 1.6 The loader's copy of the body class has no CheckNames row

`Na__LeLoad__BODY_CLASS = 'na-layout-editor--active'` copies the mode controller's `Na__LeMode__BODY_CLASS`, which
neither app exports, so there is nothing for CheckNames to read (a row reading an unexported name fails G2 pass 3).
The constant's comment says so; the class is TV's (K2 S3) and every stylesheet that uses it is TV's or Boot.

### 1.7 Smaller points

- **Which presses put the class on.** Only `Na__LeLoad__Enter` and `Na__LeLoad__OpenSpecification` (enters = true),
  and only while IsAvailable; never a quiet load (the re-stamp) or a Dev action (CreateSheet, Duplicate, Require ...).
  A Dev action still shows the boot cover, below the strip and without the class, so on localhost the 3D furniture
  (z 1001+) sits above it for those few seconds. The "+" tab and the Dev menu's create-then-open: the open usually
  lands within the cover's two-frame hide, so IsShown is still true and FirstOpen goes up `immediate`.
- **The strip is visible during a cold load now** (it was under the z 9999 cover). Pressing the 3D Model tab during the
  load is answered false by `Na__LeLoad__Leave` (nothing loaded yet) and the drawing still opens when the load
  completes. No stuck state; noted for W1-34, which rewrites the strip's handlers.
- **Cold OpenSpecification before W1-34.** It is unreachable in today's strip (1.5.0 shows the Specification tab only
  while a sheet is open). Until W1-34 routes it through EnterUnder, a cold call would enter non-quietly and get the
  `immediate` first-open veil over the specification page (follow-up 2).
- **The loader's finally is synchronous now**, so a long action that returns a promise still hides the screen as it
  starts, as the loader's own comment always said.
- **Versions**: patch steps (Loader 1.1.2, LoadingScreen 1.0.2, ModeController 1.18.2) per this run's rule and the
  W1-31/W1-32 precedent; R4's "1.2.0 / 1.1.0 / 1.19.0" labels are Adam's to relabel. LoadingVeil takes TV's 1.1.0
  (DR-34 (a)).

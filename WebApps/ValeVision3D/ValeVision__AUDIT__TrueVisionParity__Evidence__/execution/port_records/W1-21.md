## 1. Decisions taken inside the package (for the orchestrator's eye)

### 1.1 RenumberSheets without a register block: no drawing number written, the tab order still numbered

The vv_adaptation says "RenumberSheets is a no-op without a LayoutEditor__DrawingRegister block". TrueVision's
RenumberSheets does two things: it numbers `Sheet__Order` 1..n down the tab order (its v2.48.0 job, the function's own
header: "Number Sheet__Order 1..n Down the Tab Order") and, since v2.70.0, it stamps `Sheet__Fields__DrawingNumber`
from the register's series - from the config's series when the project has no register block, which is what the seam
exists to stop ("or it will stamp D01..Dnn over hand-typed numbers", S03b b4 (3); acceptance 2: "leaves every stored
Sheet__Fields__DrawingNumber untouched while no register block exists"). The seam landed as one line that keeps the
first job and drops the second:

```js
if (!data.LayoutEditor__DrawingRegister) { sheets.forEach((sheet, index) => { sheet.Sheet__Order = index + 1; }); return; }   // <-- ValeVision: no Drawing Register block, no drawing number written (DR-11); the tab order alone, 1..n
```

Why not a bare `return;`: `DeleteSheet` relies on RenumberSheets for its order, so a bare return leaves a gap after
every delete (orders 1, 3) - and a never-numbered sheet's drawing number is now TrueVision's default, prefix + its
`Sheet__Order` ("D01"), so the tabs would read D01, D03 where TrueVision (and this app before, which renumbered on
delete) read D01, D02. With the line above every tab reads what TrueVision shows for a never-numbered pack, no stored
number is ever written, and TrueVision's v2.48.0 delete fix (keep a dragged tab order) comes across too. Evidence:
harness section C; mutation_check "strict no-op" fails exactly "Sheet__Order stays 1..n" and "seam removed" fails
exactly "every stored number untouched". If the orchestrator prefers the literal no-op, the line becomes
`if (!data.LayoutEditor__DrawingRegister) return;` and the PORT NOTE's Divergences bullet loses its "numbers
Sheet__Order" clause - nothing else changes.

### 1.2 The loader's tab code follows the drawing number with its default (W1-19 F3)

With TrueVision's Sheets unit the model's GetShortCode cuts the code from `Na__LeRec__DrawingNumber` (stored number,
else "D" + the padded `Sheet__Order`), so the toolbar, the Sheet panel and the specification chips read
"D01 - Plans" for a never-numbered sheet. The loader's GetShortCode / GetDrawingNumber / GetTabLabel read the stored
number only (Loader :792-793 before), and TrueVision's tab strip 2.0.0 reads its Drawings menu rows, their hover and
the "is open" title through them - so after this package the strip would have said "Plans" beside a toolbar saying
"D01 - Plans". W1-19 F3 assigned this to W1-21; the loader is in this package's edits. The loader now applies
TrueVision's rule line for line (`Na__LeLoad__DrawingNumber`), with the register's prefix and digits read from the
editor's config once it has loaded (`editor.config.Na__LeCfg__GetDrawingRegisterSetup`, proved by G2 pass 3) and the
records' own fallbacks (D, two digits) before - this app's config holds D and 2, so the answer is the same either side
of the load (LoaderFacade's before/after checks, and harness H against the real model). A typed empty number still
shows the name alone, as TrueVision's does. The DrawingCode leaf is not grown (DR-42 default "none happen").

### 1.3 The late start, exactly as TrueVision's

No VV seam was needed in the facade: this app's mode controller initialises the model, History, AutoSave, the
specification and its links in one synchronous `.then` (ModeController :1088-1137), so TrueVision's microtask lands
after all of them listen and before the loader carries on (S03b verifier, confirmed here by the harness's mark order).
Deleting `Na__LeLoad__AnnounceProjectLoad` in the same change is required: with the old loader and the new model the
load is announced twice (harness control "mixed").
